Lab 0 说明文档
=============

范围：本实验的编码部分——`webget`，一个基于操作系统流式套接字 API 构建的 HTTP/1.1 客户端，以及内存中的流控字节流。手动网络练习（telnet/SMTP）不在范围内。

ByteStream 的设计：
该字节流是一个具有固定容量的流控 FIFO 缓冲区。它将字节存储在一个 `std::string` 中，外加一个 `_buffer_start` 偏移量，用于标记第一个尚未被弹出的字节；因此 `buffer_size()` 就是 `_buffer.size() - _buffer_start`，并且它永远不会大于容量，因为 `write()` 只接受 `min(data.size(), remaining_capacity())` 个字节。

`pop_output()` 只是推进偏移量，只有在整个缓冲区被排空时（清空它）才会触及存储，或者在至少一半已死*且*已死字节超过 4096 字节时（擦除已消费的前缀）才会触及存储。由于一次压缩只会在被弹出的字节数至少等于被它拷贝的字节数之后发生，所以一次 pop 的均摊成本是 O(1)，并且对超长流进行逐字节读取的读者不会退化为二次方行为。

两个计数器 `_bytes_written` 和 `_bytes_read` 是独立累加的，而不是推导出来的，因此它们会持续统计那些已经从缓冲区中丢弃的字节。`eof()` 是 `input_ended() and buffer_empty()`：到达流的末尾既要求写者关闭了输入，也要求读者已经消费了所有仍然缓冲的内容。

实现中的挑战：
这个类本身很小；棘手的地方在于 `input_ended()` 和 `eof()` 之间的区别。一个写者已经关闭但其缓冲区仍持有字节的流会报告 `input_ended() == true` 和 `eof() == false`，只有当最后一个字节被弹出后它才会翻转为 `eof()`。测试 "write-end-pop" 和 "write-pop-end" 恰好锁定了这种顺序。

对于 `webget`，请求的每一行都必须以 CRLF 结尾，并以一个空行结束；使用 `endl` 或 `"\n"` 会让服务器永远等待请求的剩余部分。回复也必须在循环中读取，直到套接字到达 EOF——服务器可以随意将它拆分到任意多个 TCP 段中，所以单次 `read()` 很容易只返回正文的一部分。`Connection: close` 正是使回复的结束可被观察到的原因：服务器关闭它那一半流，下一次 `read()` 返回 0 并设置 EOF 标志。
